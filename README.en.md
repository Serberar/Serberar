### Good software shows when you have to change it.

I design and build products end to end: domain model, API, interface, tests and deployment. I favour code that someone else can understand, test and change without fear.

<table>
<tr>
<td width="33%" valign="top">

**Architecture**

Isolated domain, ports and adapters. Business rules depend on neither the framework nor the database, and tests keep it that way.

</td>
<td width="33%" valign="top">

**Product**

From problem to production. Clear interfaces, error states designed on purpose and decisions that can be explained to the people who use them.

</td>
<td width="33%" valign="top">

**Security**

Least privilege, validated input, secrets out of the code and verified downloads. Store only the data you need.

### Principles

1. **Understand before writing.** The smallest change that solves the whole problem.
2. **Test behaviour.** A test is worth the failure it prevents, not the coverage it adds.
3. **Fail clearly.** Log the full error and tell the user what they can do.
4. **Automate what repeats.** Tests, build and release on every change.
5. **Document just enough.** A README that gets you running and explains why.
